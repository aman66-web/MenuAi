# Review of the unfinished improvement pass (branch claude/menumacros-kit)

Written 30 October 2026. The improvement pass (about 28 bug fixes and four small features, commit 62114fe on `claude/menumacros-kit`) was reviewed by three
independent reviewers (correctness, project rules, accessibility). Their 19 findings are below, as they wrote them. A second agent checked 11 of them and confirmed 9.
The step that would have fixed them stopped at a usage limit, so **none is fixed yet** except these two, fixed by hand before the WIP commit:
- keys.json regenerated (findings 2 and 8);
- `web/e2e/sharelist.mjs` line 190 now uses `getByText("Quantity 2", { exact: true })` (part of finding 5).

Before this pass can ship: apply the findings, run the production build and every browser suite (README in web/e2e), write its docs/PROGRESS.md entry (its new copy is listed in the
implementers' reports: Shopping list cleared., Removed “{name}”., Recently added, Log a serving, Add to today, Added to today., Last 7 days, the Average a day lines,
the Try … hint pieces, Page not found, This page doesn't exist or has moved., Add a photo, Change photo, Remove photo), and merge `main` into it first (main now has the 1.4.1 sources fix).
Finding 6 and the Sainsbury's rebuild in finding 7 need the founder's yes.

## Findings

   - What goes wrong: Open /app/today with nothing logged today. The empty state now shows an "Add food" button that goes to Home. This wording was not part of the approved copy for this change.
   - Fix: Get the founder's approval for "Add food" here, or log it in PROGRESS as reused 2026-10-14 copy, then regenerate keys.json.
2. **[minor, correctness]** `web/lib/mm/locales/keys.json`:1: keys.json was not regenerated, so tests/i18n.test.ts fails and `./scripts/test.sh --unit` is red. The file lacks 27 new keys and still lists the removed "Try a higher calorie limit, a lower protein or fewer allergies."

   - Fix: Run `WRITE_I18N=1 npx vitest run tests/i18n.test.ts` once all copy is approved. Note that "Page not found" and "This page doesn't exist or has moved." (web/app/not-found.tsx) sit outside the scanned folders and won't be listed.
3. **[minor, correctness]** `web/app/app/settings/page.tsx`:327: "Clear everything" does not remove the two new sessionStorage keys, mm.eatOutChoices (holds the Halal choice) and mm.chainView. The privacy page says Clear data removes preferences, but these survive it. It already removes mm.browseType and mm.finder.
   - What goes wrong: On Eat out, open More ways and tap Halal (stored as mm.eatOutChoices {halalOnly:true}). Go to Settings › Clear data › Clear everything and finish onboarding in the same tab. Eat out still opens with Halal on and lists only halal chains, though all settings were reset. Each restaurant's stored sort and opened sections also survive.
   - Fix: Add sessionStorage.removeItem("mm.eatOutChoices") and sessionStorage.removeItem(CHAIN_VIEW_KEY) beside the existing removals.
4. **[minor, correctness]** `web/app/app/eat-out/eatOutChoices.ts`:33: Regression: once any Eat out choice is stored for the tab, the person's saved Halal diet setting is no longer used. Before, every visit to Eat out started with halalOnly equal to settings.preferences.halalOnly.
   - What goes wrong: Tap "Full nutrition only" on Eat out (stored {moreOpen:true, fullOnly:true, halalOnly:false}). Then turn on Halal in Settings › Diet and allergies and go back to Eat out. The list shows non-halal restaurants with the Halal chip off; before this change it started filtered to halal. This is the same kind of complaint as the founder's 2026-10-11 "diet settings ignored".
   - Fix: Store the saved halal value alongside the choices and drop the stored halalOnly when settings.preferences.halalOnly has changed since. Or re-apply the saved setting whenever it changes.
5. **[minor, correctness]** `web/e2e/addfood.mjs`:88: Moving Home's toast to UndoToast breaks existing browser tests. UndoToast writes the message twice (a hidden status line plus the visible pill), so page.getByText("Added “…” to …").waitFor() hits Playwright strict mode. Separately, sharelist.mjs still uses getByLabel("Quantity 2"), and the aria-label it matched was replaced by sr-only text.
   - What goes wrong: Running e2e/addfood.mjs fails at lines 88, 110, 262, 317, 330, 343 and 422 (two elements match the text, including lines the eatout agent added). Running e2e/sharelist.mjs fails at line 190 because tesco.getByLabel("Quantity 2").count() is 0.
   - Fix: In addfood.mjs use page.getByRole("status").filter({ hasText: … }) (as days.mjs and extra.mjs now do). In sharelist.mjs:190 use tesco.getByText("Quantity 2", { exact: true }).

   - What goes wrong: `npx vitest run tests/i18n.test.ts` fails 1 of 13 tests. keys.json is missing every new string from the four agents ("Shopping list cleared.", "Removed “{name}”.", "Recently added", the five "Try {a}…" sentences and their pieces, "Log a serving", "Add to today", "Added to today.", "Last 7 days", the two "Average a day…" lines, "From {n} days…", "Add food", "Add a photo", "Change photo", "Remove photo") and still lists the removed "Try a higher calorie limit, a lower protein or fewer allergies.". 9. **[major, rules]** `web/e2e/addfood.mjs`:88: The new UndoToast prints the toast text twice (the sr-only role=status line and the visible aria-hidden span), so every `page.getByText("Added “…” to …").waitFor()` in addfood.mjs now matches two elements and fails Playwright's strict mode.
   - What goes wrong: Home's 'Added' pill is now `<UndoToast top …>`. It renders `<p role="status" class="sr-only">Added “Toast and jam” to Dinner.</p>` plus `<span aria-hidden>` with the same words. getByText ignores aria-hidden, and the 1 px sr-only element counts as visible, so `waitFor()` throws a strict-mode violation. This hits the old steps (lines 88, 110) and the steps the eatout agent just added with the same pattern (lines 262, 317, 330, 343, 422). The addfood e2e suite fails at its first add.
   - Fix: Use `page.getByRole("status").filter({ hasText: "Added “…” to …" }).waitFor()`, as days.mjs, extra.mjs and listadd.mjs already do. Or scope the locator to the visible pill.
10. **[major, rules]** `web/e2e/sharelist.mjs`:190: A8 removed the `aria-label="Quantity n"` from the shared-list quantity, but sharelist.mjs still counts `getByLabel("Quantity 2")`, so its 'pictures, prices and quantities' step now fails.
   - What goes wrong: SharedListBody now renders `<span aria-hidden>×2</span><span class="sr-only">Quantity 2</span>` with no label. `tesco.getByLabel("Quantity 2").count()` returns 0, the `=== 1` check is false and the step throws. Both the groceries agent's report and the brief say this line needed changing, but sharelist.mjs is not in the diff.
   - Fix: Change it to `tesco.getByText("Quantity 2", { exact: true }).count() === 1`, as groceries.mjs and listadd.mjs now do.
11. **[minor, rules]** `web/app/app/settings/page.tsx`:327: 'Clear everything' still removes only mm.browseType, mm.finder and mm.sharedAdded from sessionStorage. The two new keys, mm.eatOutChoices and mm.chainView, survive a clear, so restored Eat out filters keep applying afterwards.

12. **[minor, rules]** `web/app/app/groceries/search/SearchScreen.tsx`:45: A25 is incomplete: "Search every shop" still picks its default shop from the raw `settings.shops`, so a saved Co-op (catalogue count 3) is still treated as the person's shop.

13. **[minor, rules]** `web/app/app/_components/UndoToast.tsx`:24: UndoToast never clears `heldKey` when the toast closes. If the same toast key comes back (deleting the same restored entry or saved order again), the timer is treated as held and the pill never goes away on its own.
   - What goes wrong: Desktop, Today page. Delete entry A (toast key `deleted:A`), move the mouse over the pill (heldKey = `deleted:A`) and click Undo. The pill is removed under the pointer, so React never gets onPointerLeave and heldKey stays. restoreLogEntry puts back the same id. Delete A again: the key is `deleted:A` again, `held` is true at once, the effect returns without starting a timer, and the pill stays until the pointer enters and leaves it. The same happens in My meals (`deleted:${order.id}`) and after a keyboard Undo when no blur fires on removal.
   - Fix: Reset heldKey when the message closes or its key changes, for example `useEffect(() => setHeldKey(null), [key])`, or clear it in the Undo click handler and in onDone.
14. **[minor, rules]** `web/app/app/_components/AppShell.tsx`:63: Tab memory records an address only when the pathname changes, so filters the new code keeps in the query (Recipes ?meal/only/cuisine/occasion, a shop list's ?aisle/sort/card) are never remembered when the person switches tabs.

16. **[major, accessibility]** `web/app/app/_components/UndoToast.tsx`:20: Keyboard, switch and VoiceOver users can't reach the new Undo before it disappears. The timer only pauses once Undo itself has focus or the pointer. The pill comes after the page content in DOM and tab order, and the actions that remove the focused control (Clear, '−' at quantity 1) drop focus to <body>.
   - What goes wrong: Shopping list with 10 items. A keyboard or switch user tabs to the '−' of the 3rd item (quantity 1) and presses Enter. The row unmounts, focus falls to <body> and "Removed “…”." is announced. To reach Undo they must tab through the 7 remaining rows (tick, product link, −, + each), the 'Add more from …' rows, Share/Copy/Send/Remove ticked/Clear and the 'You might also need' block: about 40 stops. The 8 s timer keeps running all the while, so Undo is gone first. Clear is the same: the Clear button unmounts with the list, so focus is lost and VoiceOver starts from the top. 'Log a serving' (Undo comes after every ingredient row, Swap and 'I have this' button and the method) and My meals' 'Log' (after the rest of the saved-order list) are effectively unreachable too. The component's own comment says it lets 'a keyboard or switch user reach Undo in time', and the brief asked for exactly that. This is the only way to recover a wiped, synced shopping list.
   - Fix: When the action removes the control that had focus (Clear, '−' at 1, and Delete on Today and My meals), move focus to the Undo button. When Undo is used or the toast times out, put focus back somewhere sensible (the list heading, or the next row's '−'). Alternatively, keep the timer paused while document.activeElement is <body> or outside the page after the action, and render the toast next to the triggering control in DOM order. Add an e2e step that presses Enter on '−' at quantity 1 and reaches Undo with Tab or with focus already on it.
17. **[minor, accessibility]** `web/app/app/meals/RestaurantMeals.tsx`:132: My meals' new 'Log' toast sits at the bottom, where the Undo can land exactly on a saved order's right-most 'Log' pill. A second tap on Log then undoes the first log instead of logging again. Home's toast is kept at the top to rule this out ('a second tap on the same + must never land on Undo').
   - What goes wrong: 390 px iPhone with the home bar. The toast occupies about 146–202 px from the bottom (bottom 7rem + safe area, about 56 px tall). Its Undo spans x≈298–366. A saved order's button row scrolled to just above the tab bar puts its 'Log' pill (the right-most SOFT_PILL, x≈274–354) in that band. The person taps Log to log the meal and taps Log again for a second portion. The second tap hits Undo: the first entry is deleted, nothing new is logged, and the pill vanishes, so it looks as if it worked. The trash buttons at the cards' top right are in the same column, so a Delete there can hit Undo too.
   - Fix: Put this toast where none of the triggering controls can be: at the top as on Home (the toast already supports `top`), or ignore taps on Undo for the first ~600 ms after the toast appears. Add an e2e check that the Log pill's rectangle and the Undo's don't overlap at the scroll position where Log was tapped.
18. **[minor, accessibility]** `web/app/app/recipes/RecipeDetail.tsx`:471: The 'Logged to Today.' toast sits at the top. Its Undo lands exactly on the picture's 'Save' heart pill (same top inset, both at the right). A tap on Save within 8 s deletes the serving that was just logged, and the recipe isn't saved.
   - What goes wrong: Tall phone (430×932) or a short recipe name, so the picture's top is on screen when 'Log a serving' is tapped, or the person scrolls back up within 8 s. Hero pills sit at pt-[max(0.75rem,safe-top)] px-4, with Save at the right (≈ x 330–414, y 59–103). The toast is inset-x-4 at top max(0.75rem,safe-top), with Undo at its right end (pe-2). Back (left) is covered by the toast's text and does nothing. The implementer noted that it 'covers the Back/Save pills', but not that the covered spot is Undo.

19. **[minor, accessibility]** `web/app/app/_components/UndoToast.tsx`:36: The always-mounted status line only announces when its text changes. A second toast with the same words is never read, and several new toasts have fixed words: 'Logged to Today.', 'Added to today.', and 'Added “X” to Lunch.' for the same Recently added row.
   - What goes wrong: On a past day in Today, a VoiceOver user taps 'Add to today · Lunch' and hears "Added to today.". They then tap 'Add to today · Dinner' within 8 s. The toast's key changes and the timer restarts, but <p role=status> still holds the identical string, so React writes nothing to the DOM and the second copy is never announced. The same happens when logging two saved orders in a row on My meals, logging a second serving on a recipe page, or re-adding the same Recently added item. A sighted user also sees an unchanged pill.
   - Fix: Make each new message a change the live region will announce. Empty the status line and set the text on the next frame when the key changes, or alternate between two status elements by key, or add a hidden per-key suffix. Naming the meal or order in the text would also work, but that is a copy change and needs the founder's approval (rule 8).
